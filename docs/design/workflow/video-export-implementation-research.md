# Video editor and export implementation research

**2026-10-10 · recommendation for implementation planning.** This covers [E01–E09](workflow-state-contract.md#8-finished-video-editing-and-export), the shared request rules and [EDIT-01–13](acceptance-cases.md#edit). It does not implement or deploy anything. Sources were inspected on this date; cloud deployment state was not inspected.

Use **a dedicated Node/Express export service running a pinned FFmpeg build**, with Firestore records and private GCS objects. Keep generation providers out of the renderer. Use a pure shared composition validator/compiler for browser preview and server rendering. Do not revive the retired sequence editor or broad replay workers.

## Composition and timing decisions

These are concrete proposed initial limits, to be copied into the capability policy and qualified before enabling export:

- Three MP4 presets: 1920×1080, 1080×1920 and 1080×1080, **30/1 fps**, H.264 `yuv420p`, SDR BT.709, AAC stereo 48 kHz. Other rates, HDR, transitions, speed changes and effects stay unavailable. Changing the preset still requires E02's visible fit/fill/crop choices.
- Maximum 60 seconds, 32 visual items, 100 text cues, 256 KiB composition JSON, 512 MiB aggregate source bytes, and five minutes of aggregate source decoding. Enforce bounds against streamed bytes and probe results, not uploaded metadata alone. A file already stored in Vidra can still exceed an editor capability; identify that source and retain the edit.
- A newly inserted still lasts **three seconds / 90 frames**, visibly editable. It has silence. An inserted video uses its available interval; exceeding composition limits makes the edit invalid rather than silently trimming it.
- Store half-open integer frame intervals `[inFrame, outFrame)` and composition-frame anchors. One output frame is exactly 1,600 samples at 48 kHz. UI time entry snaps to the nearest frame, with ties upward, and displays the snapped time before commit. Bounds validation happens after snapping; do not clamp a bad interval silently.
- Clip-attached text/audio stays relative to its clip; background audio stays relative to the composition. Compilation expands these into absolute frame/sample intervals. Insert/remove/reorder/trim/replace implement E08–E09 as pure reversible commands; an invalid caption remains present with its error.

Each saved revision stores the original exact media version IDs and the normalization version used for editing. An accepted export additionally captures composition content/hash, preset, source object generation/checksum/probe metadata, resolved timing/crops, text layout, font hashes, renderer image digest and operational limits. Later preferences, edit revisions or renderer releases cannot change it. The export-settings draft is the execution draft; accepting it does not consume or lock the video edit.

### Variable frame rates and audio

Normalize the **editor timebase**, not the stored original. Produce/cache a 30 fps display proxy and a manifest describing the source-to-editor timing. Final rendering uses that same normalization policy against the pinned source bytes. Fix the first presented video frame as time zero; preserve audio's offset from that origin, trimming earlier samples or padding silence as appropriate. Independently resetting video and audio to their own start times would lose synchronization.

Choose nearest timestamp rounding explicitly for VFR-to-CFR conversion. The last selectable boundary comes from the normalized frame count, not a rounded container-duration string. Audio trims and placements use integer samples; absent/short source audio is padded with silence for its visual interval. Background audio ends at the composition boundary without looping. Gains are recorded linear values, initially 1.0 for source audio and 0.25 for newly added background audio. Mix the specified tracks without hidden normalization or ducking; show a clipping warning and preserve the entered gains. Automatic loudness processing is outside this version.

FFmpeg provides frame-rate conversion, frame/sample trimming, timestamp adjustment, concatenation and overlays. Its trim filters do not themselves reset timestamps; concat requires compatible streams starting at zero. Set these explicitly, including dimensions, sample aspect ratio, color conversion and channel layout. Use decoded-frame/sample trimming, not stream-copy cuts at keyframes. [FFmpeg filter reference](https://ffmpeg.org/ffmpeg-filters.html)

## Preview and typography

Use one compiled plan for source intervals, crop rectangles, text placement and audio scheduling. Browser playback uses normalized proxies, a single playback clock and `requestVideoFrameCallback` media timestamps; pause for missing/buffering media instead of letting text/audio advance independently. Frame stepping waits for the requested decoded frame before displaying the corresponding overlays. Browser callbacks expose presentation timestamps but are not a guarantee that every frame was presented. [Browser frame callbacks](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/requestVideoFrameCallback)

Render captions to transparent PNG overlays using the **same pinned resvg WebAssembly artifact and bundled font bytes in browser and worker**. The upstream project supports custom font buffers, browser WASM and running WASM in Node. This is a new dependency. The server rebuilds overlays from the revision rather than trusting client-uploaded caption pixels. [resvg implementation/documentation](https://github.com/thx/resvg-js)

Offer two packaged static font faces initially, regular and bold, with recorded licenses/hashes. Define wrapping and explicit line breaks in the shared layout plan; store output-pixel position, size, line height, alignment, color and background. Disable system-font fallback and external resources. Validate glyph coverage from the bundled fonts, cue bounds and text boxes; unsupported glyphs, missing fonts or overflow produce element-specific errors. Never silently substitute fonts or clip words. Escape text into an internally generated SVG; users cannot submit SVG/filter expressions as captions.

Preview/export parity means matching selected source frames, cuts, crop geometry, text pixels and audible timing. Browser hardware decoding, scaling and lossy MP4 encoding prevent a promise of identical screenshots everywhere. Use server-rendered reference frames in acceptance tests, with explicit image-error tolerances after encoding; compare caption overlays before encoding exactly. A high-quality export does not require introducing a browser-based final renderer.

## Render, persistence and cancellation

1. **Accept:** Flush the edit, verify owner/writability and all sources, validate the saved revision, then atomically write the export request, both J01 uniqueness bindings, fixed output slot, capacity reservation and outbox obligation. No network calls or process launches inside a retryable Firestore transaction. [Firestore transactions](https://firebase.google.com/docs/firestore/manage-data/transactions)
2. **Resolve:** Read owned object handles pinned to generation/checksum through server credentials. Download into an attempt-specific private directory with byte/time limits. No signed/public URLs, network protocols, external subtitles or arbitrary paths reach FFmpeg. A missing source enters bounded reconciliation; an unrecoverable or unauthorized source fails with its version/item ID. Never render black placeholders or a different version.
3. **Execute:** Claim an immutable attempt with a fencing token. Compile validated data to an argument array and generated filter file; use `spawn` with `shell: false`, bounded logs, `-nostdin`, fixed thread counts and cancellation. Admit only selected decoded streams and local-file/pipe protocols. Use machine-readable `-progress` for processed time, distinct from storing/linking progress. [Node subprocess API](https://nodejs.org/download/release/latest-v20.x/docs/api/child_process.html), [FFmpeg CLI](https://ffmpeg.org/ffmpeg.html), [protocol restrictions](https://ffmpeg.org/ffmpeg-protocols.html)
4. **Verify:** A successful exit is necessary but insufficient. Probe dimensions, codec, frame rate and frame count; fully decode the bounded result, inspect audio presence/timing, and hash bytes. Use a finalized MP4 with fast-start metadata. A partial file is never downloadable. Existing [completion evidence code](../../../scripts/ops/provider-quality/completionEvidence.ts) demonstrates probe/decode/hash checks but needs stricter stream/frame/audio assertions and streaming hashes. [ffprobe](https://ffmpeg.org/ffprobe.html), [MP4 muxer](https://ffmpeg.org/ffmpeg-formats.html#mov_002c-mp4_002c-ismv)
5. **Store and link:** Stream to `users/{owner}/exports/{exportId}/{attemptId}.mp4` using create-only `ifGenerationMatch: 0`. Verify stored size/checksum/generation; a 412 is reconciled against expected bytes rather than overwritten. Commit the immutable media/slot mapping with attachment pending, then authoritatively attach to the project or owner recovery inbox. Only then report Ready. GCS object finalization and Firestore attachment are separate commits; the durable obligation bridges them. [GCS preconditions](https://cloud.google.com/storage/docs/request-preconditions), [storage consistency](https://cloud.google.com/storage/docs/consistency)

Before encoding, cancellation can be confirmed transactionally. During execution, persist cancellation intent, send SIGTERM, escalate to SIGKILL after a short grace period, and wait for process close before confirming. Signal delivery alone is not proof of termination. If verified completion won first, retain the file and apply J11. Lease loss aborts publication under the stale token; reconciliation checks the exact attempt and object, not merely the latest status timestamp.

Storage/link retries reuse the same object and output ID and never invoke FFmpeg again. If the only completed bytes were on ephemeral disk and disappear before durable upload, record output loss honestly; saving cannot repair absent bytes. Definitive render failure requires the user's new `retryOf` export request against the same captured revision. Duplicate queue delivery or lease expiry never silently starts another render.

## Deployment shape and bounds

**Required new infrastructure:** one private Cloud Run render service; one Cloud Tasks queue; a narrow Firestore-outbox trigger/dispatcher; scoped service accounts/IAM; export/outbox indexes; private derived-media/export storage prefixes; and a renderer-image build with fonts and a startup capability check. Reuse the existing Firebase project, GCS service integration and API authentication pattern. Do not require generation API keys, Redis, Kubernetes or existing generation-worker loops.

The API commits the outbox with acceptance. A Firestore document trigger enqueues a deterministically named task containing only the export/attempt identity, using OIDC to the private service. Duplicate trigger/task delivery is expected; the request store is the authority. Returning HTTP success means processing or a recorded terminal/recovery result is durable, not that fire-and-forget FFmpeg work was started. Add a narrowly scoped delayed reconciliation task before execution, so crashes and exhausted delivery attempts cannot strand a record forever; it only checks/reconciles this export and never authorizes a new render. [Firestore triggers](https://cloud.google.com/run/docs/triggering/trigger-functions-with-firestore-documents), [Cloud Run with Tasks](https://cloud.google.com/run/docs/triggering/using-tasks), [duplicate delivery](https://cloud.google.com/tasks/docs/common-pitfalls)

Start qualification with one render per instance, 2 vCPU, 4 GiB RAM, a size-limited 2 GiB scratch volume, two maximum instances, and queue concurrency two. Reserve renderer capacity in Firestore as well; deployment scaling settings alone are not a spend/capacity ledger. Process visual segments sequentially and remove temporary segments when safely consumed; avoid opening every decoder at once. Bound output to 512 MiB and validate scratch estimates before dispatch, with runtime byte enforcement.

Proposed policy: nine-minute attempt wall deadline, ten-minute task deadline, eleven-minute service request timeout; three bounded delivery/storage-repair attempts; twenty-minute automatic recovery deadline, then Needs attention under J13. Keep the HTTP task request open while working. Trap shutdown, stop accepting work and preserve evidence; Cloud Run gives a short termination grace period and its ordinary writable filesystem consumes memory and disappears with the instance. These are starting limits to prove with stress fixtures, not measured capacity claims. [Cloud Run runtime contract](https://cloud.google.com/run/docs/container-contract)
