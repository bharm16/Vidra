## Behavior and ownership

- Keep the safe same-origin destination through sign-in, signup, forgot-password and reset. Reject off-site or invalid destinations and authorize the resolved resource before rendering private data. Never transform a legacy ID by string substitution.
- Signing in must not execute an unrelated draft. An adopted guest draft keeps its words and remains unsubmitted. A different account cannot adopt another owner’s private drafts.
- An account can be created even when its verification email fails. Retry delivery for that account; never create a duplicate account. Verification outcomes and authenticated session state remain separate.
- A reset link is validated before password entry. Missing, expired, used, wrong-mode and temporarily failed checks retain their distinct recovery actions. Never store passwords or action codes in draft history, telemetry, or URLs beyond the provider-owned action link.
- Provider errors use user-facing recovery language. Firebase configuration instructions belong in operator diagnostics, not the sign-in interface. Google, email, and embedded-browser limitations have separate presentations.
- Legal/help navigation must preserve the active authentication return context. Open legal material separately or preserve the in-memory form on return; never persist a plaintext password to achieve this.
- Sign-out clears private rendering while its status is pending or uncertain. The unsaved-draft confirmation assumes an owned local copy exists; the no-local/no-remote-copy case remains governed by workspace R04.
- Support prepares a mail draft. A handoff attempt is not proof an email app opened, a message was sent, or a ticket was received. Feedback, security and account-deletion intent must survive the handoff. Requesting deletion does not itself purge data.
- Search and menu overlays preserve their calling page. Doc search result selection navigates to that article. Closing search returns to the caller with its state retained.
- Profile edits are not saved until acknowledged. Keep a failed edit visible for retry. Show the sign-in method from trusted account data, not from the email domain.
- Free-testing limits do not block saved media, editing or downloads. Billing is an empty free-testing surface; paid pricing and checkout activation are not inferred from this design.

## Verification

All 207 catalog entries resolve to native frames. The new page has no detected text/container overflow, no legacy master references, Inter-only interface type, and no private project image dependency in the authentication screens. Every shared component passed the layout-container audit. All prototype destinations resolve; 16 reviewed journeys have no missing consecutive step. There are 1,745 prototype transitions, including illustrative timed responses.

This is a design prototype, not a running application. Fields, account records, requests and responses are fixed examples. Live authentication, email delivery, provider output, persistence, rendering, accessibility behavior and commercial activation still require implementation and their assigned tests.
